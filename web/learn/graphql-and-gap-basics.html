GraphQL & GAP Basics

New to GraphQL or agent gateways? This zero-jargon guide builds your intuition from scratch: why AI agents benefit from one unified menu, how Types work like labeled boxes, and how a query mirrors JSON 1:1.

What you'll learn

  • Visualize a GAP Supergraph as a single coordinated order counter in front of REST, SQL, gRPC, MCP, and Code backends.
  • Read schemas effortlessly: Object types (shop_CustomersResult), Scalars (Int, String, JSON), Enums, Lists, and Non-Null (!).
  • Use the Interactive Query Builder below to toggle fields and watch valid GAP-QL match its JSON output 1:1.

Mental Model: One Order Counter vs. Twenty Separate Vendors

Imagine an AI assistant is a dinner guest arriving at a busy food court with twenty specialized kitchens: one serves customer profiles (REST API), another tracks shipping orders (SQL database), and a third keeps support notes (MCP server).

  • Without GAP (Flat Direct-MCP): Before taking a single order, the host hands the agent every binder from all 20 kitchens at once—hundreds of thousands of tokens of repetitive JSON schemas. Worse, combining a customer with their notes forces the agent to walk back and forth turn-by-turn.
  • With GAP (A Typed Supergraph): GAP places one unified, menu-indexed order counter in front of every backend. Instead of memorizing every recipe up front (203,421 tokens at 1,000 tools), the agent holds 5 tiny ordering tools (651 tokens), looks up only the dish it needs, and submits one structured request.

Supergraph & Branch in Plain English

Think of the Supergraph as the combined menu compiled by GAP, and each backend kitchen (shop, notes, billing_sql) as one Branch inside that menu.

Types Are Labeled Shipping Boxes (! Means Guaranteed)

Every GraphQL and GAP schema is just a contract describing which labeled boxes exist and what fits inside each box:

Schema building blocks illustrated with Walking Skeleton examples
Building BlockSchema ExamplePlain Meaning
Object Typetype shop_CustomersResult { id: Int! name: String! tier: ... }A structured record representing one domain entity (like a customer row from OpenAPI).
ScalarInt, String, Boolean, JSONA leaf value where selection stops—there are no deeper nested { ... } subfields inside a scalar.
Non-Null (!)id: Int! vs. name: StringThe exclamation mark guarantees GAP will never return null for that field on success.
List ([...])orders(customer_id: Int): [shop_OrdersResult!]Returns zero or more items of that type in an array.
Enumshop_CustomersResultTier (vip, standard)A fixed allowlist of string values validated before hitting backends.
Going deeper: Why does customer_notes(customer_id: 1) have NO curly braces after it?

In examples/walking-skeleton, the OpenAPI REST endpoints (shop_CustomersResult, shop_OrdersResult) compile into strongly typed Object types whose subfields you select inside { id name tier }. By contrast, external MCP tool customer_notes(customer_id: Int!): JSON returns the custom JSON leaf scalar—so writing customer_notes(customer_id: 1) { notes } triggers a GraphQL validation error! Treat scalars as leaves with zero brace sub-selection.
