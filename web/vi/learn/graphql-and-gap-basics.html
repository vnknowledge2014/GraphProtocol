Nhập môn GraphQL & GAP

Mới làm quen với GraphQL hay AI Gateway? Tài liệu nền tảng không dùng biệt ngữ này giúp bạn nắm trực giác từ gốc: vì sao Agent cần một thực đơn thống nhất, Kiểu dữ liệu giống hộp dán nhãn ra sao, và cách truy vấn phản chiếu JSON 1:1.

Bạn sẽ nắm được gì

  • Hình dung Supergraph GAP giống một quầy gọi món trung tâm trước hàng chục bếp REST, SQL, gRPC, MCP và Code.
  • Đọc thông thạo schema: Kiểu Object (shop_CustomersResult), Scalar (Int, String, JSON), Enum, Mảng và Non-Null (!).
  • Bấm chọn trường ngay trong Bộ dựng Truy vấn Tương tác bên dưới để xem GAP-QL khớp JSON đầu ra 1:1.

Tư duy Nền: Một Quầy Gọi Món so với Hai Mươi Xe Hàng Rời Rạc

Hãy tưởng tượng AI Agent là một thực khách bước vào khu ẩm thực lớn có 20 gian bếp riêng: gian bán hồ sơ khách hàng (REST API), gian theo dõi đơn hàng (SQL), và gian giữ ghi chú hỗ trợ (MCP server).

  • Khi chưa có GAP (Direct-MCP phẳng): Trước khi kịp gọi món đầu tiên, hệ thống dúi cả 20 cuốn thực đơn dày cộp vào tay Agent — tiêu tốn hàng trăm nghìn tokens JSON lặp đi lặp lại. Tệ hơn, muốn ghép khách hàng với ghi chú, Agent phải tự chạy đi chạy lại từng lượt một.
  • Khi có GAP (Supergraph định kiểu chặt chẽ): GAP đặt duy nhất một quầy tiếp nhận đã đánh chỉ mục ở phía trước mọi backend. Thay vì nhồi toàn bộ công thức ngay từ đầu (203.421 tokens ở 1.000 tools), Agent chỉ cầm 5 công cụ chuẩn (651 tokens), tra đúng món mình cần và gửi một phiếu yêu cầu gộp.

Hiểu nhanh Supergraph & Branch

Supergraph là bản thực đơn hợp nhất do GAP biên dịch sẵn, còn mỗi hệ thống phía sau (shop, notes, billing_sql) chính là một Branch (nhánh) nằm trong thực đơn đó.

Kiểu Dữ liệu Như Chiếc Hộp Dán Nhãn (! Là Cam kết Không Rỗng)

Schema trong GraphQL và GAP thực chất chỉ là bản hợp đồng mô tả rõ có những chiếc hộp dán nhãn nào và bên trong mỗi hộp chứa kiểu dữ liệu gì:

Các thành phần cấu tạo schema minh họa qua Walking Skeleton
Thành phần SchemaVí dụ Minh họaÝ nghĩa Dễ hiểu
Object Type (Đối tượng)type shop_CustomersResult { id: Int! name: String! tier: ... }Một bản ghi có cấu trúc đại diện cho thực thể (ví dụ dòng khách hàng lấy từ OpenAPI).
Scalar (Giá trị lá)Int, String, Boolean, JSONGiá trị nguyên thủy nơi câu truy vấn dừng lại — không bao giờ mở ngoặc { ... } chọn tiếp bên trong scalar.
Non-Null (!)id: Int! so với name: StringDấu chấm than cam kết GAP không bao giờ trả về null cho trường này khi truy vấn thành công.
List (Mảng [...])orders(customer_id: Int): [shop_OrdersResult!]Trả về một danh sách chứa không, một hoặc nhiều phần tử cùng kiểu.
Enum (Tập chọn cố định)shop_CustomersResultTier (vip, standard)Danh sách hằng số định sẵn được kiểm tra hợp lệ trước khi chạm tới backend.
Tìm hiểu sâu hơn: Vì sao customer_notes(customer_id: 1) KHÔNG mở ngoặc nhọn phía sau?

Trong examples/walking-skeleton, hai endpoint REST OpenAPI (shop_CustomersResult, shop_OrdersResult) được biên dịch thành Object Type định kiểu rõ các trường nên bạn chọn { id name tier }. Ngược lại, công cụ MCP ngoài customer_notes(customer_id: Int!): JSON trả về kiểu scalar lá JSON — nên viết customer_notes(customer_id: 1) { notes } sẽ bị lỗi cú pháp GraphQL ngay! Hãy nhớ: scalar là điểm lá, không mở ngoặc chọn con.

Truy vấn Phản chiếu JSON 1:1 (Bộ dựng Truy vấn Tương tác)

Khác với REST URL nơi server trả về cố định toàn bộ 40 trường dù bạn chỉ cần tên, câu truy vấn GAP-QL đóng vai trò như một khuôn mẫu JSON: bạn hỏi trường nào thì kết quả trả về đúng cấu trúc y hệt trường đó, không thừa một byte.

Tích chọn Trường để Dựng Câu Truy vấn Walking Skeleton Sống
