# WP-M4-07 Steps — Proposal workflow, persistence, DiscoveryWorker, admin API and CLI

Assumptions: `SqliteContextStore` does not yet implement `gap_store::AuditLog` (`WP-M6-11`), so `gap-ingest` supplies an `AuditLog` adapter (`ContextStoreAuditLog`) backed by `ContextStore` while allowing any custom `AuditLog` implementation to be injected. `crates/gap-cli/tests/cli.rs` line 509 asserts top-level `gap proposals ...` stays staged until `WP-M7-01`, so the `proposals` subcommand module is implemented and tested inside `crates/gap-cli/src/proposals/**` without altering `cli.rs` or `tests/cli.rs`.
Rejected simpler alternative: Storing proposals only in memory instead of `ContextStore` would lose durability and tenant-scoped queries across restarts; storing unchained audit entries would violate `INV-14`.
Risks: `crates/gap-ingest/Cargo.toml` lacks a direct `serde`/`serde_json` dependency, so persistence serialization uses `CisgValue::to_canonical_json()` paired with a small typed JSON parser plus primitive `NewNode.props` fields.
