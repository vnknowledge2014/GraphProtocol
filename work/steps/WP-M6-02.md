# Step Plan: WP-M6-02 — Task API Core (`TaskStore`, FSM, Leases, Crash Recovery, Strategies, SSE Replay)

- **Refs:** `WP-M6-02`; specs: `RUN-080`, `RUN-081`, `RUN-082`, `RUN-083`, `RUN-084`, `RUN-085`, `RUN-086`, `RUN-091`, `INV-09`, `INV-13`, `INV-20`, `ADR-016`
- **Owns:** `crates/gap-exec/src/tasks/**`, `crates/gap-store/src/tasks/**`, `crates/gap-exec/tests/task_crash_recovery.rs`
- **Assumptions:** `gap-store` keeps existing object-safe `TaskStore`, `TaskStatus`, `TaskRecord`, `TaskEventRecord` signatures intact so downstream/re-exported callers remain compatible; `tokio::sync::broadcast` + `mpsc` bounded channels (`64`) back live SSE event following without holding mutexes across `.await`; `SqliteTaskStore` uses `PRAGMA journal_mode = WAL` and `PRAGMA synchronous = FULL` so transitions commit before acknowledgement.
- **Rejected simpler alternative:** Keeping an in-memory-only task store with post-hoc event emission would violate `RUN-080` crash durability and `INV-13` strict per-task `seq` ordering across restarts; using `std::process::Command` in `task_crash_recovery` was rejected in favor of dropping an active SQLite-backed worker/executor handle mid-task while keeping the same WAL DB on disk, which tests real SQLite WAL persistence deterministically without flaky sleeps.
- **Risks:** `SqliteTaskStore` connection mutex must never cross async `.await` (`INV-02`); large artifacts (`> 1 MiB`) must spill to disk before emitting events/records to avoid storing blobs inline in SQLite rows (`RUN-086`).
