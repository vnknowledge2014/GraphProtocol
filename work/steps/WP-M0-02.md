# WP-M0-02 steps — Workspace, pinned dependencies, cargo-deny, crate skeletons

- **Assumptions:**
  1. Host sandbox is strictly offline and forbids installing new binaries (`cargo-deny` is not installed). Rust `1.98.1`, `cargo 1.98.1`, `rustfmt`, `clippy`, Git, and Python 3.11+ (`tomllib`) are available locally.
  2. Every workspace member crate (`crates/*`, `adapters/*`, `bench/*`) declares only intra-workspace `path` dependencies (via `[workspace.dependencies]`) and zero third-party dependencies in `WP-M0-02`, allowing `cargo generate-lockfile --offline`, `cargo build --workspace --locked --offline`, `cargo clippy --workspace --all-targets --offline -- -D warnings`, and `python3 tools/check_layers.py` to execute completely offline without a populated Cargo registry cache.
  3. All third-party library crates that already have verified version strings in `docs/evidence/crate-versions.md` (55 crates) live exclusively in root `[workspace.dependencies]` (`ADR-002`), while `rhai` (`ADR-019` deferred), `a2a-rs` (replaced by vendored `a2a.proto`), CLI subcommands (`cargo-nextest`, `cargo-fuzz`, `cargo-deny`), and unpinned crates (`blake3` marked `(verify)`, plus planned crates not yet listed in `crate-versions.md`) are omitted and documented in `docs/evidence/crate-versions.md` and the handoff.
  4. Module stubs listed by `python3 tools/wp.py modules` use `<mod>/mod.rs` wherever downstream WPs own `src/<mod>/**` (61 modules across 15 crates, plus nested `extractors/*` and `gates/*` stubs in `gap-ingest` so concurrent WPs `WP-M4-02` and `WP-M4-03` never collide on `extractors/mod.rs`), and `src/wiring_s1.rs` in `crates/gap-server` because `WP-M5-03` owns `crates/gap-server/src/wiring_s1.rs`.
- **Rejected simpler alternative:**
  - *Alternative A:* Give every skeleton crate an empty `[dependencies]` table and zero Rust tests. Rejected because wiring valid lower-layer intra-workspace path dependencies now exercises `tools/check_layers.py` (`ARC-001` and `ARC-002` transitive reachability) on real workspace edges, prepares the four multi-WP crates whose `Cargo.toml` is not owned by a single downstream WP (`gap-sec`, `gap-ingest`, `gap-s1`, `gap-mcp`), and adding a real `std`-only test in `gap-testkit` provides executable traceability for `ARC-001` and `ARC-003`.
  - *Alternative B:* Create flat `src/<mod>.rs` files for all module stubs. Rejected because 61 of the 62 module ownership globs in `work/work-packages.toml` are `src/<mod>/**` directory globs; a flat `src/<mod>.rs` file would lie outside the downstream WP's `owns` glob.
- **Risks:**
  1. `cargo-deny` is absent on this host, so `deny.toml` cannot be validated by `cargo deny check` locally; mitigated by authoring strict `cargo-deny` 0.20 schema (no deprecated v0.14 keys, valid SPDX identifiers from `ADR-002`, no unmatched exceptions/wrappers), validating TOML structure via Python `tomllib`, reporting acceptance command 3 as `NOT RUN`, and leaving `WP-M0-02` in `doing` state.
  2. `tools/spec_trace.py` treats `ADR-*` inside `spec:` markers under `crates/**` or `adapters/**` as unknown requirement IDs; mitigated by tagging code tests strictly with `spec/` requirement IDs (`// spec: ARC-001, ARC-003`) and referencing `ADR-002` only in prose comments.
  3. Global Git config outside the workspace is blocked by the sandbox; mitigated by passing `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null` so Git uses the existing `.git/config` author identity unmodified.
